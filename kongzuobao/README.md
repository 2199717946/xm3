# 空座宝 · 校园自习室空位地图

面向大学生的自习室查询原型。核心解决一件事：**把"跑空"这件不确定的事，变成确定的。**

对应《第二个软件作品设计》里的功能点：

| 设计文档里的功能 | 原型里的实现 |
|---|---|
| 实时空位地图 | `地图` 页的座位图，每 6 秒自动刷新；后端有模拟线程持续推新状态 |
| 按楼栋楼层筛选 | `找座` 页的楼栋 / 楼层 chips |
| 一键预约并到点提醒 | 座位详情抽屉 →「预约这个座位」；到点前 15 分钟弹提醒 |
| 有无插座筛选 | 「只要有插座的座位」开关，座位图上有 ⚡ 角标 |
| 安静程度筛选 | 可讨论 / 较安静 / 静音区 |
| 同行人数筛选 | 1 人 / 2 人 / 3-4 人，按空位数过滤 |
| 门禁 + 插座 + 众包三路数据 | 每个座位带「数据来源」，支持同学一键上报纠错 |
| 无广告、免注册、3 秒出结果 | 打开就是首屏统计 + 推荐，没有任何登录流程 |
| 9.9 元/月会员 | `我的` 页可开通，解锁优先预约与更长预约时长 |

## 接口一览

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/meta` | 楼栋 + 楼层 + 各楼空位统计 |
| GET | `/api/overview` | 首屏：全校空位、推荐自习室、热门预约 |
| GET | `/api/rooms` | 筛选自习室，参数 `building_id` `floor_id` `socket` `quiet` `people` `q` |
| GET | `/api/rooms/<id>` | 单间自习室详情 + 完整座位图 |
| POST | `/api/reserve` | 预约座位 `{seat_id, user, minutes}` |
| GET | `/api/reservations?user=` | 我的预约 + 待触发的到点提醒 |
| POST | `/api/reservations/<id>/cancel` | 取消预约，座位立即释放 |
| POST | `/api/report` | 众包上报 `{seat_id, user, claim: free\|occupied}` |
| GET | `/api/reports` | 最近上报记录 |
| GET/POST | `/api/member` | 查询 / 开通会员 |

## 数据表

- **building** 楼栋 → **floor** 楼层 → **room** 自习室 → **seat** 座位，四级一层层往下
- **seat** 每行带 `status`（`free` / `occupied` / `reserved`）、`has_socket`、
  `source`（这条状态是门禁、插座还是众包得出的）、`updated_at`
- **reservation** 预约，含 `remind_at`（到点前 15 分钟）和 `reminded` 标记，保证只提醒一次
- **report** 众包上报，写入的同时立刻修正座位状态
- **member** 会员

## 关键实现说明

**"实时"是怎么来的。** 真实场景下座位状态由门禁刷卡记录和插座用电网关推上来。
原型里 `app.py` 的 `simulate_tick()` 每 6 秒随机翻转一小批座位（约占总数 1/40），
模拟"有人来、有人走"，前端同步轮询刷新。接真实数据时，把这个函数换成
消费消息队列即可，接口层完全不用动。

**预约不会打架。** 预约失败的座位返回 409，前端提示"手慢了"。
预约到点未签到会自动释放（`expire_finished()`），减少占座纠纷——这正是设计文档里
"避免占座纠纷"那一条。

**空位风险分级。** 空位率 ≥35% 显示"去了就有座"，15%~35% 是"还有空位，早点去"，
低于 15% 是"快满了，建议先预约"。绿色/橙色/红色三档，且都带文字说明，
不靠颜色单独传达信息。

**配色是刻意分开的。** 绿色只用来表示"空闲"这个状态，不做品牌色；
应用主色用蓝色。这样"绿色 = 有座"这件事在整套界面里含义唯一，不会产生歧义。

## 部署成线上版本

线上跑和本地跑有三处不一样，代码里已经处理好了，改之前先看这一节。

### 1. 先跑部署前自检

```bash
python deploy_check.py
```

它会在**临时数据库**上把全部接口走一遍（不会动 `kongzuobao.db`），重点验证三件
本地看不出、上线才炸的事：库路径能否用环境变量改、时间是否真的是东八区、
WAL 是否生效。34 项全 PASS 再往下走。

### 2. 只开一个进程

```bash
gunicorn app:app --workers 1 --threads 8 --timeout 60 --bind 0.0.0.0:$PORT
```

`--workers` **必须是 1**。`app.py` 在导入时会启动"实时数据"模拟线程，开 N 个 worker
就会有 N 份模拟同时改同一批座位：状态以 N 倍速乱跳，还会互相抢 SQLite 写锁。
单核免费实例用 `1 worker + 8 线程` 完全够撑演示。

真要多进程，就得把 `simulate_tick()` 拆成独立进程（或换掉它去消费真实数据流）。

### 3. 环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `PORT` | `5000` | 监听端口，平台一般会自动注入 |
| `KONGZUOBAO_DB` | 源码目录下 `kongzuobao.db` | 数据库路径。容器里要指到挂载的持久卷 |
| `RUN_SIMULATOR` | `1` | 设 `0` 关掉模拟线程，座位状态保持静态 |

### 4. Render 免费部署

`render.yaml` 已经写好了构建与启动命令，不用手填。

1. 把项目推到 GitHub（`kongzuobao.db` 已在 `.gitignore` 里，不用提交）。
2. Render 控制台 → `New +` → `Blueprint` → 选这个仓库。
3. 等构建完，拿到 `https://xxx.onrender.com` 这个永久 https 地址。

**免费实例的两个已知行为**，演示前心里有数：

- **会休眠**：约 15 分钟没人访问就停，下次打开要等 30~60 秒冷启动。
  答辩前先自己点一下把服务唤醒，别让评委等。
- **磁盘是临时的**：重新部署后数据库重建，回到干净的示例数据。
  对演示来说是好事（永远是最新状态），但别拿它存要留的东西。

国内直接访问 onrender.com 速度一般。要给老师现场看，可以先本机
`python app.py` 再配个内网穿透（Cloudflare Tunnel / cpolar），走国内线路更稳。

## 后面怎么接着做

原型验证完，往正式产品走的话：

1. **换前端**：`app.js` 里每个函数对应的就是一个接口，直接翻译成小程序的
   `wx.request` 即可，WXML 的写法跟现在的 HTML 结构基本一一对应。
   （小程序上线还需要主体资质和服务器域名备案，周期比部署这个网页版长得多。）
2. **换后端**：`app.py` 用的是标准 WSGI，换服务器只是换启动命令；
   SQLite 换 MySQL 时只需改 `db.py` 里的连接与少量 SQL。
3. **接真实数据**：替换 `simulate_tick()`，改为消费门禁/插座的实时数据流，
   然后把 `RUN_SIMULATOR` 设成 `0`。
4. **要给人真的用**：得先补多用户隔离——现在预约的 `user` 是前端传上来的字符串，
   谁都能冒充别人；另外还要加限流防刷。这是另一个量级的工作。
